## Root Cause

The Turbopack/runtime failure was caused by repository-root filesystem pollution plus stale generated Next state.

Evidence:

- Eight generated Lighthouse/Chrome profile directories were directly inside the repository root.
- One `undefined:` Lighthouse residue directory was directly inside the repository root.
- These directories contained Windows/WSL-style path fragments such as `\\wsl.localhost`, `undefined:`, `undefined`, and `AppData/Local/lighthouse.*`.
- They contained browser cache/profile internals such as `GPUPersistentCache`, `GPUCache`, `Code Cache`, `Default/Cache`, `Default/Service Worker`, and `CacheStorage`.
- The polluted files were Git-tracked, not merely untracked local files.
- `next.config.ts` correctly pins `turbopack.root = process.cwd()`, which means Turbopack scans the repository root. Since the illegal browser-profile paths were inside that root, they were visible to Turbopack/file watching.
- `.next` also contained generated state from earlier runs and was removed before rebuilding.

Likely symptom mapping:

- `Unable to add filesystem: <illegal path>`: caused by the Windows/WSL-style Lighthouse profile paths inside the repo root.
- `Unexpected Turbopack Error`: caused by Turbopack encountering/scanning those illegal path names or stale generated dev graph state.
- `_clientMiddlewareManifest.js` MIME/runtime errors: consistent with stale dev runtime/browser requests after Turbopack graph corruption. After cleanup, the correct dev URL `/_next/static/development/_clientMiddlewareManifest.js` returned `200 OK` with `Content-Type: application/json`.
- `GET / 500`: not reproduced after cleanup. `GET /` returned `200 OK` in dev.

## Config Review

Reviewed:

- `next.config.ts`
- `tsconfig.json`
- `pnpm-workspace.yaml`
- `package.json`
- lockfiles

Findings:

- `next.config.ts` already has the correct Turbopack root pin:

```ts
turbopack: {
  root: process.cwd(),
}
```

- This avoids parent workspace-root misdetection, but it cannot protect against illegal generated directories placed inside the repo itself.
- `tsconfig.json` has broad includes such as `**/*.ts`, `**/*.tsx`, `.next/types/**/*.ts`, and `.next/dev/types/**/*.ts`. This was not the direct pollution cause because the browser cache files are not TypeScript sources.
- `pnpm-workspace.yaml` only contains build approval settings; it did not cause the scan issue.
- No config changes were required.
