# Component Architecture

## Purpose

Define how frontend components should be organized, reused, tested, and separated between shared UI, layouts, and feature-specific modules.

## Scope

Applies to all React components in:

- `src/components/ui`
- `src/components/layout`
- `src/components/shared`
- future feature component folders

## Responsibilities

Frontend developers own:

- Component APIs.
- Reuse boundaries.
- Accessibility.
- Story or example usage if added later.

Backend developers influence:

- Data shape requirements.
- Status enums.
- Validation messages.

## Architecture Overview

```txt
shadcn/ui primitives
  -> shared platform components
    -> route/page components
      -> feature-specific forms and tables
```

## Component Categories

| Category | Examples | Rules |
| --- | --- | --- |
| UI primitives | Button, Card, Dialog, Table | Generated by shadcn; keep close to source |
| Layout | PublicShell, DashboardShell | Own navigation and page frame |
| Shared | EmptyState, PageHeader, DataTable | Reusable across modules |
| Feature | ResidentForm, PaymentTable | Domain-specific; keep near feature |
| Provider | AppProviders | Cross-app wrappers |

## Server vs Client Components

Server Components:

- Page shells.
- Data display with server-fetched records.
- Static public sections.

Client Components:

- Forms.
- Dialogs/sheets.
- Dropdown actions.
- Interactive filters.
- Toast-triggering actions.

## Component API Guidelines

- Use typed props.
- Avoid passing raw database rows deeply.
- Prefer view models for UI-specific shape.
- Keep business decisions out of presentational components.
- Keep components small enough to test and reuse.
